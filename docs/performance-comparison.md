# Rust 版与 Go 版性能对比

本文记录 v2node 节点端从 Go 版迁移到 Rust 版时的同机实测结果。结论只适用于本文描述的测试环境，不应直接外推为所有机器、所有协议组合的通用结论。

## 结论摘要

- **常驻内存是差异最大的指标**：空载时 Rust 约为 Go 的 1/7–1/8；40 条保持连接时约为 1/3–1/4；远端并发后的内存峰值约为 1/4。
- **并发场景**：16 并发 × 1 MiB 下，Rust 完成时间为 Go 的约 78%–85%（快约 15%–22%），服务端 CPU 少约 30%–40%。
- **单流吞吐**：Rust 略快，但差距明显小于内存和并发场景，不构成数量级提升。
- **延迟**：同连接 RTT 基本同级；新连接握手 Rust 略快。
- **公网吞吐**：经过 Cloudflare 和隧道后，绝对值受链路抖动主导，只能作为趋势参考。
- **部署体积**：Rust 是约 10 MiB 的静态单文件；Go 版约为 77 MiB 二进制加约 27 MiB geoip/geosite 数据。该差异包含功能范围差异，不能理解为同等功能下体积缩小 7 倍。

## 测试环境与方法

- **对比时间**：2026-11-10。
- **Rust 版本**：v0.1.0（static-pie musl x86_64）。核心 VLESS 数据面在 v0.1.1 和 v0.2.0 未改变；v0.2.0 新增的可配置 `ListenBacklog` 未纳入本轮测试。
- **Go 版本**：v0.4.6（使用 Go xray-core）。
- **测试节点**：单 vCPU，无 AES-NI、无 AVX；节点上同时有真实用户流量。Go 与 Rust 交替切换，使用同一份面板配置、同一监听端口和同一 Cloudflare 入口。
- **加密**：未开启 VLESS Encryption。
- **本机测试**：`vless_probe` 直连节点监听端口，避免公网链路干扰。
- **公网测试**：构建机上的官方 Xray 26.11.9 客户端经 Cloudflare 访问 `speed.cloudflare.com`，Go 与 Rust 交替执行。
- **测试项目**：
  - 8 MiB 单连接 TCP 回显；
  - 16 并发 × 1 MiB TCP 回显；
  - 64 B 同连接 RTT，500 次；
  - 64 B 首包新连接，20 次；
  - 公网 5 MiB 下载、2 MiB 上传；
  - 公网 16 并发 × 1 MiB。

测试包含多次交替运行，表中范围为实测波动区间。单 vCPU、无 AES-NI 且存在真实流量，绝对值和尾延迟都会受到噪声影响。

## 内存

单位：MiB，取 RSS；峰值取测试期间的高水位。

| 场景 | Go v0.4.6 | Rust v0.1.0 |
|---|---:|---:|
| 空载 | 55–64 | 7.7–8.0 |
| 40 条保持连接 | 60.3–64.6 | 15.0–21.9 |
| 远端并发后的峰值 | 65.8–67.3 | 14.3–16.2 |

Rust 的主要收益来自更小的运行时和更少的每连接缓冲开销。连接数增加后，Rust 内存仍会增长，因此“1/7”只适用于空载场景；有连接时更接近“1/3–1/4”。

## 吞吐与 CPU

本机直连，未开加密。

| 场景 | Go v0.4.6 | Rust v0.1.0 | 差异 |
|---|---|---|---|
| 8 MiB 单连接回显 | 189 / 251 ms | 153 / 184 ms | Rust 略快，服务端 CPU 均约 0.04–0.05 s |
| 16 并发 × 1 MiB | 616 / 762 ms，CPU 0.19–0.20 s | 481 / 651 ms，CPU 0.11–0.14 s | 完成时间为 Go 的约 78%–85%，CPU 少约 30%–40% |

两种实现均为 16/16 成功。单流场景的差异不大，说明 Rust 的收益主要集中在并发调度、每连接内存和 CPU 效率，而不是单条连接的极致吞吐。

## 延迟

| 指标 | Go v0.4.6 | Rust v0.1.0 |
|---|---:|---:|
| 64 B 同连接 RTT p50 | 130 µs | 126–150 µs |
| 64 B 同连接 RTT p99 | 248–556 µs | 194–411 µs |
| UDP p50 | 146–154 µs | 149–157 µs |
| early data p50 | 127–133 µs | 141–145 µs |
| 64 B 首包新连接中位耗时 | 约 2 ms（1–22 ms） | 约 1 ms（1–5 ms） |

同连接 RTT、UDP 和 early data 基本处于同一水平，互有胜负，差异在噪声范围内。Go 在首包只有 1–16 B 时存在约 1003 ms 的固定延迟路径，首包达到 64 B 后恢复到 1–2 ms；生产环境真实的 TLS/HTTP 首包通常不小于 64 B，因此不应把这个 1 秒当作通用生产延迟。

## 公网路径

经 Cloudflare 和隧道访问 `speed.cloudflare.com`，网络抖动较大。

| 场景 | Go v0.4.6 | Rust v0.1.0 |
|---|---:|---:|
| 5 MiB 下载中位速度 | 约 1.8 MB/s | 约 3.1 MB/s |
| 2 MiB 上传中位速度 | 约 0.73 MB/s | 约 0.85 MB/s |
| 16 并发 × 1 MiB 总耗时 | 5.40 / 8.92 s | 3.72 / 7.47 / 8.59 s |

上述测试均出现十余秒级离群值，且 Cloudflare、隧道和 WAN 是主要变量。这里的数字只能说明 Rust 在该路径上不劣于 Go，不能作为公网吞吐保证。

## 部署体积

| 项目 | Go v0.4.6 | Rust v0.1.0 |
|---|---:|---:|
| 主二进制 | 约 77 MiB | 10,473,320 字节（约 10 MiB） |
| 额外数据文件 | geoip/geosite 约 27 MiB | 无 |
| 部署形态 | 二进制 + 地理数据 + Go xray-core 依赖 | static-pie 单文件 |

Rust 版当前未实现 routes/geo/REALITY，生产数据的 `route_id` 也为空，因此体积差异有一部分来自功能范围裁剪。该表反映的是当前节点实际部署占用，不是同等功能集的公平体积对比。

## 如何解读

1. **内存是最稳定的收益**：空载和稳定连接数下都明显低于 Go，适合小内存 VPS 和提高单机连接密度。
2. **并发效率是第二收益**：相同并发负载下完成更快、CPU 更少，为更高连接上限留出余量。
3. **单流吞吐不是数量级差异**：对单用户大文件下载，Rust 可能略快，但不应期待翻倍。
4. **公网测速不是可靠基准**：Cloudflare 和隧道抖动会掩盖节点差异；判断节点性能应看本机直连、CPU 和内存指标。
5. **未覆盖加密场景**：本轮未开启 VLESS Encryption，也没有在支持 AES-NI/AVX 的机器上重复测；不同 CPU 和加密配置会改变绝对结果。
6. **测试版本差异**：v0.2.0 将监听 backlog 从固定 128 改为可配置 4096，高并发突发建连场景可能优于本文测试版本，但本次没有重新跑该项。

仓库中的 `tests/e2e*.sh` 和 `vless_probe` 覆盖功能与压力路径；本文数字来自一次性对比测试，不是 CI 性能门禁。
