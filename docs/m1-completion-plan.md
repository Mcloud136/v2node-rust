## 1. 结论摘要

M1 的**功能面已全部交付**：VLESS/WS 数据面、四种 TLS 模式、ACME 双挑战、VLESS Encryption 三模式、面板五接口、用户热更新与限流计量均已实现，并有单测、探针、E2E 与 Xray 互通证据。

但 M1 **尚不能宣布验收关闭**，原因是唯一未闭环的验收项 **P2-2（真实 Let's Encrypt + Cloudflare）** 仍被外部输入阻塞，且工程收尾项（P1-3、P2-3、P2-4）与质量门禁尚未落地。

建议将 M1 关闭标准收敛为「P2-2 staging 验收 + 生产 cert_mode 决策 + 文档同步」，把 P1-3/P2-3 归入 M1.1，避免收尾项拖长 M1 关闭时间。

### 3.2 依赖关系

```text
[外部输入 T0: CF Token / 测试子域 / 运行授权]
        │
        ├──> P2-2a (DNS-01) ──> P2-2b (HTTP-01，可选) ──> P2-2c (生产决策) ──> M1 关闭
        │                                                │
        │                                                └──> Q-2 (证书告警)
        │
[P1-3] ──> [P2-3]        （M1.1，字段分类复用）
[Q-1]  ──> [P3-2]        （CI 复用交叉构建）
[P2-4] ──> [P3-1] / [P3-3]（同一运维窗口 / 日志策略）
[面板 API] ──> [P3-4]    （跨仓库依赖）
```

关键耦合点：

1. **P2-2 与 Q-2**：真实签发验证的是「能不能签」，告警解决的是「到期会不会漏续」，两者必须同批，否则 P2-2 的收益无法持续。
2. **P1-3 与 P2-3**：两者都改 listener 启动路径。P1-3 引入 `ListenBacklog` 字段后，P2-3 的「非 bind 变更原位应用」需要把它归入可热更新参数，顺序不能反。
3. **P2-4 与 P3-1/P3-3**：同属日志与磁盘策略，必须一次窗口决定，避免反复改 systemd 单元。
4. **Q-1 与 P3-2**：arm64 制品需要可复现的 CI；先有门禁再有制品，否则每次手工构建都无法保证一致性。

### 3.3 优先级判定理由

- **P0 只给 P2-2 与文档/发布口径**：P2-2 是 M1 唯一未闭环的验收项；文档与版本口径决定「发布出去的东西是否自洽」，两者都不做则 M1 无法关闭。
- **P1 给 P1-3 与 Q-2**：前者是容量前提（内核已调 8192，应用层仍 128），后者是证书生命周期的兜底；都不阻塞上线，但决定「能否安全放量」。
- **P2 给 P2-3/P2-4/P3-1/Q-1**：属于工程与运维收尾，可在 M1.1 完成。
- **P3 为可选**：无当前业务驱动，按需启动。
- **M2 独立立项**：REALITY/routes/0-RTT 是协议能力扩展，不应与收尾混在一起。

## 6. 自我审查

### 6.1 合理性

1. **把 P2-2 设为唯一 P0 是合理的**：它是 M1 唯一「代码完成但未验收」的项，其余未完成项都是工程收尾或可选增强。
2. **把 P2-3 移出 M1 是必要修正**：原计划把它排在 W3 会直接挤压 M1 关闭评审，且它是 5–8 天的高风险重构，不应与验收绑定。
3. **P1-3 列为 P1 而非 P0 是合理的**：生产当前无容量故障，`MaxConnections=4096` 与 backlog 128 的矛盾属于「潜在瓶颈」而非「正在失血」。
4. **不合理之处**：2.3 的权重与完成度是主观判断，不能当作精确度量；它只用于排序，不应用于对外汇报「87% 完成」。

### 6.2 可行性

1. **P2-2 可行性高**：脚本已落地、语法校验通过、真实 LE 账户创建已验证，剩余是输入而非开发。
2. **P1-3 可行性高**：改动集中在 `listener.rs` 与 `config.rs`，1 天可完成；但「backlog 生效」的生产验证需要窗口，不能只看单测。
3. **P2-3 估算偏乐观**：涉及 `NodeRuntime` 生命周期、listener 原位更新、TLS/ACME 重载、失败回滚，5–8 天是下限；若要求「连接零中断」，实际可能 8–12 天。**建议按 8–12 天重估，并拆成「字段分类」「原位应用」「回滚与回归」三个可独立验收的子任务。**
4. **Q-1 估算偏低**：GitHub Actions 上跑 musl 交叉构建 + clippy + 测试，首次配置通常 1–2 天；若同时做 P3-2，需再加 1–2 天。

### 6.3 潜在遗漏

1. **测试环境建设未列入**：这是最大遗漏。所有 E2E 依赖 Linux 构建机或生产机；没有稳定测试环境，P2-2 之后的每次回归都要借生产机。
2. **证书生命周期监控只列了告警，没有列「续期失败重试策略」**：`acme_loop` 每 24h 检查一次，失败只 warn；若连续失败 3 天，需要升级告警级别。
3. **文档同步范围不完整**：只列了 README 与配置口径，未列 `docs/vless-encryption-prod.md` 的「已完成提示」触发条件（该文档第 8 节是硬约束）。
4. **版本策略未定义语义化规则**：P1-3 是功能新增，按 SemVer 应为 `v0.2.0` 而非 `v0.1.2`；计划里写 `v0.1.2` 与此矛盾。
5. **P3-4 的面板侧工作无人认领**：只写了「面板 API 支持」，没有面板侧任务、排期与验收。
6. **P3-5 的不可逆性未在任务里体现**：应在删除前 `git stash show -p > backup.patch`，否则违反「stash 是唯一留存」的事实。

## 附录 D：srv85 实机对比（2026-11-11）

**方法**：在 srv85（Ubuntu 20.04，NodeID 10）上以隔离实例对比三个二进制：端口 20109–20111，状态、日志与 spool 均在 `/tmp/v2node-bench`，mock 面板监听 19090。**未触碰** `/etc/v2node-rust`、systemd 单元与生产进程；测试结束后删除临时目录并复核生产 PID 未变。

需要说明的口径：仓库里的 `0.1.1` 线上二进制实际已包含 P1-3 / P2-3 / P3-4 代码（当时未升版本号），因此它不等同于 `0.1.0`。下表中 `0.1.0` 取节点上的原始备份，`0.1.1` 取当前线上二进制。

| 指标 | 0.1.0（原始） | 0.1.1（线上） | 0.2.0（新） |
|---|---:|---:|---:|
| SHA256 前 12 位 | `27727f68274f` | `4e4667a451c0` | `40a406fa0646` |
| 体积（字节） | 10,473,320 | 10,506,312 | 10,559,784 |
| 启动到监听（ms） | 92 | 57 | 55 |
| RSS（KB，空载） | 6,320 | 6,248 | 6,152 |
| `ListenBacklog=1024` 时 Send-Q | **128** | 1024 | 1024 |
| 热更新为 `2048` 后 Send-Q | **128（不变）** | 2048 | 2048 |
| 改运行参数是否重建 runtime | **是（1→2）** | 否（1→1） | 否（1→1） |
| `config applied in place` 日志 | 0 | 2 | 2 |
| 非法 spool 文件被读取并告警 | 0 | 0 | **1** |
| 重绑后进程 PID 稳定 | 是 | 是 | 是 |

生产基线（只读采集）：`0.1.1`、PID `940086` 全程未变、RSS 20.4 MB、Send-Q 4096、服务 active。

**结论**

1. `ListenBacklog` 确实穿透到内核：0.1.0 固定 128，0.2.0 随配置从 1024 变到 2048；PID 不变说明是 listener 重绑而非进程重启。
2. 配置热更新已由「重建 node runtime」变为「原位应用」，实机行为与代码一致。
3. `TrafficSpoolPath` 在 0.2.0 生效：非法 spool 文件被读取并告警，0.1.x 完全无此行为。
4. 启动耗时与空载内存无回退；三者差异在测量噪声范围（±10 ms / ±200 KB），不作为性能结论。
5. 生产实例 RSS（20.4 MB）远高于空载实例，属真实连接与缓冲占用，不能用空载数据推断容量。
